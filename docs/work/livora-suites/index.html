Livora Suites

Livora Suites is a hotel management system for independent hotels, resorts and small groups. I designed and built both front ends: a native Windows application that works offline, and a responsive web app that lets owners check any property from a phone. They share one design language, one feature set and 17 interface languages.

(01)

Problem

  • A hotel needs reservations, front desk, housekeeping, maintenance, billing, point of sale, kitchen and bar, reports and channel management, used by people with very different jobs.
  • Existing tools are either built for big chains or too thin for a real hotel.
  • The interface had to be learnable in minutes by a new receptionist and readable at a glance by a manager.
  • It had to be safe for a cook with greasy hands on a touch screen, usable in any language and currency, and fast on an old PC and on a phone.
This led to· Software built for chains, or too thin
· Staff with very little time to learn
· One system, very different jobs

(02)

Solution

Design around roles, not pages. Each person lands on their own screen and sees only what they can use. Both front ends share one design-token system, language and recovery are treated as first-class features, and the screenshot test runs every page in every language.

(03)

Key design decisions

1.

Role-aware navigation

  • Owner, front desk, housekeeping, kitchen and bar, waiter and accountant each get their own navigation and landing page.
  • Plan-locked web features are shown with a lock rather than hidden, so owners can see what an upgrade adds.
  • Kitchen and bar staff land on their board right after sign-in.
2.

Colour means something, but never alone

  • Each KPI family and status has its own accent, so scanning beats reading on a busy front desk.
  • Chips and labels repeat the state in words, so it works for colour-blind users and in black-and-white print.
  • One primary action per screen or dialog, always in the same place.
3.

Safe for a busy kitchen

  • A dedicated board with big buttons, oldest tickets first.
  • Auto-refresh and a sound for new orders.
  • Allergy notes have their own highlighted row, because safety-critical text must stand out.
4.

Language as a first-class setting

  • 17 interface languages. Picking one suggests a country and currency; nothing is locked in.
  • Arabic mirrors the whole layout; it is not just right-aligned.
  • A screenshot self-test opens every page and dialog in all 17 languages and catches truncation, overlap and mirroring bugs.
5.

Recovery and licensing on the first screen

  • “Restore from a backup” sits on the sign-in screen, because after a reinstall it is the first thing a hotel needs.
  • The license page shows what is used, the computer code, and a one-click transfer to a new computer.

(04)

Outcome

  • Two front ends, Windows and web, built from one design-token system, with eight user roles.
  • 17 languages including mirrored Arabic, and country-based currency choice.
  • An automated screenshot test over every page and dialog in all 17 languages, plus hundreds of automated logic checks.
  • An end-to-end test against a real license server, and a simulated “reinstall the computer and restore from backup” disaster test.
  • An installable web app (PWA) with light and dark themes and live updates.

(05)

My role

  • Information architecture, ten wireframes and the design tokens.
  • Web client: ES modules, CSS custom properties, PWA, live updates and internationalisation.
  • Windows client: C# WinForms with custom-drawn, DPI-safe controls and a right-to-left helper.
  • The screenshot self-test and the logic tests.

(06)

Key takeaway

Designing for roles first, not pages first, removes most of the clutter.
